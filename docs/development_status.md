# Trailwise SDK — Development Status

Tracks progress feature-by-feature against the plan in [prd.md](prd.md). Update this file whenever a feature moves status — it is the single source of truth for "what's built" going forward.

## How to use this file

- One row per feature. Update **Status** as work progresses; don't add new tracking files elsewhere.
- Move a feature to **Certified** only when its acceptance criteria are met and verified (tests passing, manual check against the criteria noted in the row) — not just "code written."
- When a feature's scope changes, edit its row in place; use the PR/commit that changed it as the history (git blame on this file), not a changelog section here.
- Add new rows if a feature is split or a new one is identified; don't delete rows for abandoned work — mark status **Dropped** with a one-line reason instead.

## Status Legend

| Status | Meaning |
|---|---|
| 🔲 Not Started | No implementation work begun |
| 🚧 In Progress | Actively being built |
| ✅ Built | Implemented, not yet verified against acceptance criteria |
| 🏅 Certified | Implemented **and** verified against its acceptance criteria |
| ⛔ Dropped | Descoped — reason noted |

| 1.4 | Client-side PII redaction (Presidio, structured + regex first) | 🏅 Certified | Structured field-name redaction and regex scrubbing active by default; Presidio NER layer available; no raw PII in emitted logs for test fixtures | PRD §3. Implemented in [trailwise/redaction.py](../trailwise/redaction.py): `redact_structured_fields` (key-name match against `SENSITIVE_FIELD_NAMES`, case-insensitive), `redact_regex_matches` (email/credit-card-digit-run/phone patterns, in that order so an unspaced card number isn't misread as a phone number), and `pii_redaction_processor` composing both as a structlog processor. Wired into the default pipeline in [trailwise/logging.py](../trailwise/logging.py) — inserted right after `merge_contextvars`, before every other processor, so nothing downstream (including file/console renderers) ever sees a raw value. Presidio NER layer (`presidio_available`, `redact_with_presidio`) is a separate, optional tier: not on the default pipeline, gated behind a new `presidio` extra (`presidio-analyzer` + `presidio-anonymizer` + the `en_core_web_sm` spaCy model, added via `uv add --optional presidio`, pinned to a direct wheel URL in `[tool.uv.sources]` since `spacy download` needs pip which this project's uv-managed venv doesn't ship) — `presidio_available()` reports `False` gracefully when the extra isn't installed, so the base install stays light. Which spaCy model to load is a per-tenant `RedactionConfig` SQLModel row (`set_redaction_config(...)`), not an environment variable — the loaded-engine cache is keyed by resolved model name so tenants sharing a model share one loaded spaCy pipeline. Verified by 9 tests in [tests/test_redaction.py](../tests/test_redaction.py): structured redaction (type-agnostic, case-insensitive), each regex tier individually, the composed processor, an end-to-end test asserting no raw PII (email/phone/card/password fixtures) reaches an actual written log file via the real `configure()` pipeline, and a Presidio free-text test (skipped automatically if the extra isn't installed). |
| 1.5 | Fail-open wrapper around all instrumentation | 🏅 Certified | Any exception inside SDK instrumentation is caught; host application logic unaffected; verified via fault-injection tests | PRD §5, §7. Implemented in [trailwise/failsafe.py](../trailwise/failsafe.py): `fail_open` (decorator, sync- and async-aware via `inspect.iscoroutinefunction`) and `fail_open_context` (context-manager form, used inside feature 1.7's span-emit step). Catches `Exception` only — never `BaseException` (`KeyboardInterrupt`/`SystemExit`/`GeneratorExit` are control-flow signals, not instrumentation errors, and swallowing them would make the host unresponsive to shutdown) — logs a `trailwise_instrumentation_error` warning event (itself sandboxed in its own `try/except`, so a broken logging pipeline can't turn "fail open" into "fail crash"), and returns `None` instead of propagating. Deliberately asymmetric with feature 1.4's PII masking, which stays fail-**closed**: a failure to observe must never crash the host, but a failure to redact must never let PII through — documented in the module docstring so the distinction isn't lost. This wrapper protects instrumentation internals only; it is never placed around the host's own business logic, which feature 1.7's context managers confirm by design (a `ValueError` raised inside a `with tool_call(...):` block still propagates normally). Verified by 8 tests in [tests/test_failsafe.py](../tests/test_failsafe.py) (sync/async success and failure paths, `KeyboardInterrupt` passthrough, warning-event logging) plus the Stage 1 exit gate's broader chaos suite (1.9). |
| 1.6 | Prompt fingerprinting + auto version registration | 🏅 Certified | SHA-256 hash over normalized prompt template; new hash auto-registers a version; repeat hash links to existing version; default system-generated titles | PRD §8.1, §8.2. Implemented in [trailwise/prompts.py](../trailwise/prompts.py) (`fingerprint_prompt`, `register_prompt_version`, `PromptVersion` SQLModel table keyed on `(slot_name, content_hash)`). Hash covers the template text (formatting-noise normalized: stripped/rstripped lines) plus sorted-key-JSON model params, so key order never affects it and re-running the same template with different runtime variable values links to the same version rather than minting a new one. New `(slot_name, content_hash)` auto-registers with `version_number` incremented per slot and a default system-generated title (`"{slot_name} — v{n} — {iso timestamp}"`); a repeat hash returns the existing row unchanged. Shares the existing rotation-config SQLite store via `trailwise.config.get_engine()` so `PromptVersion` registers on the same `SQLModel.metadata` / same `.db` file rather than opening a second store. Verified by 9 tests in [tests/test_prompts.py](../tests/test_prompts.py) (fingerprint stability/whitespace-normalization/param-order-independence, new-version + repeat-hash + changed-template + independent-per-slot numbering). Out of scope for this pass (deferred to later features): structural diffing against the previous version (part of §8.1, no acceptance criterion here yet), human-settable titles + promotion aliases (2.7), eval-on-detection (2.8). `prompt_version_id` is already a field on `schema.LLMSpan` and threadable through `instrumentation.llm_call(..., prompt_version_id=...)` (1.7) — wiring `register_prompt_version`'s result into a live call site is left to the host app. |
| 1.7 | Decorators / context managers for instrumentation (`@trace`, `with trailwise.span()`) | 🏅 Certified | One-line integration for common call sites (LLM call, tool call, agent step) | PRD §5. Implemented in [trailwise/instrumentation.py](../trailwise/instrumentation.py): three context managers — `agent_step`, `tool_call`, `llm_call` — each a one-line `with` statement yielding the matching `trailwise.schema` span so the caller can fill in fields as they become known (e.g. an `LLMSpan`'s token counts once the provider's response arrives). Decorator sugar (`trace_agent_step`, `trace_tool_call`, `trace_llm_call`, sync- and async-aware) wraps a whole function as one step for the common case. Each context manager resolves `trace_id`/`parent_span_id` from feature 1.8's current trace context (starting a new trace if none is active), generates a new `span_id`, binds it as current for the block's duration (so nested calls auto-parent with zero manual id-passing — see the nesting test), stamps `ended_at` on exit, and emits the span as both a structured log event (`agent_span`/`tool_span`/`llm_span`, feeding the 1.1 capture pipeline) and an OTel export (1.3) — with the emit step wrapped in feature 1.5's `fail_open_context`, never the caller's own code. `tool_call` additionally sets `success`/`error_message` from whether the block raised, while still re-raising the original exception unchanged. Verified by 10 tests in [tests/test_instrumentation.py](../tests/test_instrumentation.py) (W3C-conformant generated ids, `ended_at` stamping, tool success/failure marking, LLM usage-field mutation, agent→tool parenting, trace-context restoration on exit, structured-log emission, real OTel export when opted in, decorator sugar, emit-failure isolation) plus the Stage 1 exit gate's chaos suite (1.9). LLM decorator sugar doesn't auto-populate token-usage fields from a function's return value (no assumed return shape) — use the context-manager form when usage needs recording. |
| 1.8 | W3C Trace Context propagation | 🏅 Certified | `traceparent`/`tracestate` correctly propagated across process boundaries; single propagation format used throughout | PRD §5. Implemented in [trailwise/tracecontext.py](../trailwise/tracecontext.py): `generate_trace_id`/`generate_span_id` (W3C-conformant 32/16 lowercase hex chars), `format_traceparent`/`parse_traceparent` (full `{version}-{trace-id}-{parent-id}-{trace-flags}` handling, rejecting malformed or all-zero ids by returning `None` rather than raising — fail-open posture for external/untrusted input), `bound_trace_context` (the in-process propagation primitive, `contextvars`-based exactly like `trailwise.logging.bind_context`, so it's asyncio-task-safe), and `inject_traceparent`/`extract_traceparent` for carrying the same ids through a plain header dict across a process boundary. This is the single propagation format used throughout: feature 1.7's `agent_step`/`tool_call`/`llm_call` all read `current_trace_id()`/`current_span_id()` to resolve parent linkage, and `trailwise.schema`'s spans get their ids exclusively from `generate_trace_id`/`generate_span_id`. Verified by 11 tests in [tests/test_tracecontext.py](../tests/test_tracecontext.py) (id conformance, format/parse round-trip, malformed/all-zero rejection, bind/restore, nested bind/restore, header inject/extract round-trip, isolation across concurrent asyncio tasks) plus feature 1.7's cross-span parenting test. |
| 1.9 | Latency overhead & fail-open threshold check | 🏅 Certified | Benchmark shows <5% added latency; chaos test confirms zero propagated exceptions to host | Stage 1 exit gate — must certify before Stage 2 work is certified. Verified by [tests/test_stage1_exit_gate.py](../tests/test_stage1_exit_gate.py): a latency benchmark comparing median wall-clock time of a simulated 50ms call (`time.sleep`) against the same call wrapped in `instrumentation.tool_call`, asserting overhead stays under the 5% threshold (measured ~1.1% on this dev machine, stable across repeated runs) — finding and fixing feature 1.3's uncached per-span `gen_ai_semconv_enabled` SQLite round trip (was ~11% overhead) was what got this under budget; and a chaos suite fault-injecting failures into the OTel exporter (parametrized across all three span types), the structlog logger, and both simultaneously, confirming none of them ever propagate out of `agent_step`/`tool_call`/`llm_call` — paired with tests confirming a genuine host business-logic exception (e.g. a real `ValueError` raised inside the `with` block) still propagates normally, even when the exporter is simultaneously broken, so fail-open protection and real error propagation are confirmed independent of each other. |
