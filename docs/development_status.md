# Wisetraceloom SDK — Development Status

Tracks progress feature-by-feature against the plan in [prd.md](prd.md). Update this file whenever a feature moves status — it is the single source of truth for "what's built" going forward.

## How to use this file

- One row per feature. Update **Status** as work progresses; don't add new tracking files elsewhere.
- Move a feature to **Certified** only when its acceptance criteria are met and verified (tests passing, manual check against the criteria noted in the row) — not just "code written."
- When a feature's scope changes, edit its row in place; use the PR/commit that changed it as the history (git blame on this file), not a changelog section here.
- Add new rows if a feature is split or a new one is identified; don't delete rows for abandoned work — mark status **Dropped** with a one-line reason instead.

## Status Legend

| Status | Meaning |
|---|---|
| 🔲 Not Started | No implementation work begun |
| 🚧 In Progress | Actively being built |
| ✅ Built | Implemented, not yet verified against acceptance criteria |
| 🏅 Certified | Implemented **and** verified against its acceptance criteria |
| ⛔ Dropped | Descoped — reason noted |

| 2.1 | Delta-Lake-inspired append-only storage (versioned JSON commits + Parquet checkpoints + OCC) | 🏅 Certified | Writers retry on version conflict; checkpoints compact every ~10 commits; time-travel by version/timestamp works | PRD §1, §5. Implemented in [wisetraceloom/storage.py](../wisetraceloom/storage.py) (`StorageCommit`/`StorageCheckpoint`/`StorageConfig`, `append_commit`, `read_as_of_version`/`read_as_of_timestamp`/`read_latest`) and [wisetraceloom/checkpoint.py](../wisetraceloom/checkpoint.py) (pyarrow-touching compaction, kept separate to isolate that dependency's surface, mirroring the existing `config.py`/`rotation.py` split). Rows, not files: Delta's JSON-commit-files-on-object-storage design exists to fake atomic create-if-not-exists on storage with no native transactions — SQLite already has real transactions and a `(stream_id, version)` unique constraint, so the commit log is a generic SQLite table (`stream_id`/`record_type`/`payload` deliberately generic, not span-specific, so PRD §8.4's eventual `PromptVersion` migration onto this log needs no schema change). OCC: `append_commit` computes the next version via an indexed `max(version)` lookup (not `PromptVersion`'s `len(prior_rows) + 1`, which doesn't scale at commit-log volume) and retries on `IntegrityError`/`OperationalError`, raising `StorageConflictError` after `max_retries`. Checkpoints are full snapshots (not deltas) of commits `[1..version]`, written to Parquet; reads reconcile the latest applicable checkpoint plus the commits since it (an event-log replay model, not keyed-upsert). Required `wisetraceloom/config.py` changes to support real concurrent writers: WAL mode + a busy timeout + a generous connection pool (SQLite serializes actual writes regardless; the pool just needs enough slots for callers to wait on that lock instead of hitting a pool timeout), and replacing `lru_cache` on `_get_engine` with an explicit lock (plain `lru_cache` doesn't serialize concurrent *misses* of the same key, which caused a real `table already exists` race under this feature's concurrent-writer test). **Durability trade-off, load-bearing for future readers**: a synchronous SQLAlchemy-mediated SQLite write costs a few milliseconds — trivial next to a real LLM/tool call, but enough to blow the Stage 1 exit gate's <5% latency budget (feature 1.9) if it sat inline on every span (measured 17–34% overhead before the fixes below). Two changes brought it back under budget: (a) checkpoint compaction (the expensive, Parquet-writing part) runs on a background thread rather than inline in `append_commit` — checkpoints are self-healing by design (a late one just means the next interval's snapshot replays more commits), so this costs nothing correctness-wise; (b) `instrumentation.py`'s per-span hot path calls a new `enqueue_append` (bounded queue + single background writer thread, drops-and-logs if full) instead of `append_commit` directly, making automatic span persistence **best-effort, not durable-on-return** — consistent with this SDK's existing fail-open philosophy and PRD §7's own call for "local buffering/spooling... bounded queues with an explicit drop policy," but a real, deliberate scope narrowing from a literal reading of "writers retry on version conflict" for the auto-instrumented path specifically. Direct callers (tests; a future `prompt_versions` stream) still get `append_commit`'s synchronous, durable, OCC-conflict-checked write. Verified by 24 tests across [tests/test_storage.py](../tests/test_storage.py) and [tests/test_checkpoint.py](../tests/test_checkpoint.py) (OCC retry + conflict exhaustion, concurrent writers via `ThreadPoolExecutor`, checkpoint firing at #10/#20/configurable intervals, checkpoint-failure isolation, time-travel by version and timestamp, checkpoint+tail reconciliation, tenant-config fallback, fail-open on storage failure, real `tool_call` round-trip), plus a manual smoke check (12 spans through `tool_call`, checkpoint file confirmed on disk, time-travel read confirmed) and a full rerun of [tests/test_stage1_exit_gate.py](../tests/test_stage1_exit_gate.py) (still passing — no latency or chaos-guarantee regression). `pyarrow>=18.0.0` added as a required core dependency (not optional like `presidio`): checkpoint compaction is itself an acceptance criterion with no meaningful degraded mode, and pyarrow ships prebuilt wheels for every platform. Out of scope for this pass (as planned): migrating `PromptVersion` onto this log, crypto-shredding (2.2), hash-chained audit log (2.3, no `prev_hash` column added yet), retention enforcement (`StorageConfig.retention_days` field exists but is inert, no pruning job), tenant-scoped stream partitioning (single global `"spans"` stream today). |
| 2.2 | Crypto-shredding for erasure | 🏅 Certified | Per-subject key encryption; key deletion renders ciphertext unrecoverable; two-phase "Requested"→"Confirmed" erasure workflow | PRD §3, §7. Implemented in [wisetraceloom/crypto_shred.py](../wisetraceloom/crypto_shred.py) (`SubjectKey`, `ErasureRequest`, `encrypt_for_subject`/`decrypt_for_subject`, `request_erasure`/`confirm_erasure`). Each data subject gets a per-subject Fernet key (`SubjectKey`, versioned by `generation` so a subject can be re-provisioned after erasure); `encrypt_for_subject` stamps the generation used into the returned token (`"{generation}.{fernet_token}"`) so decryption always resolves the exact key a given ciphertext was encrypted under, not whatever generation happens to be active. Two-phase workflow: `request_erasure` durably records the ask (`status="Requested"`) without touching key material; `confirm_erasure` is a distinct, one-way step that destroys every still-active key generation for the subject (`key_material=None`, `destroyed_at` stamped — row kept, not deleted, so the erasure fact stays auditable), flips the request to `"Confirmed"`, and appends an immutable erasure-fact commit (subject id, request id, requester, scope, timestamps, count of keys destroyed — **never** the erased plaintext or key material) to storage's (feature 2.1) `"erasure_log"` stream via the durable, synchronous `append_commit`, not the best-effort `enqueue_append` instrumentation uses, since a dropped erasure-fact record would undermine the audit trail this workflow exists to provide. Deliberately fail-closed (raises `ErasureRequestError` on an unknown or already-resolved request id) rather than fail-open like instrumentation, matching the PRD §7 dichotomy already established by feature 1.4's redaction. Added `cryptography` as a core dependency (previously only pulled in transitively via the optional `presidio` extra and dev-group tooling) — same precedent as `pyarrow` for feature 2.1. Verified by 13 tests in [tests/test_crypto_shred.py](../tests/test_crypto_shred.py): encrypt/decrypt round-trip, per-subject key isolation (one subject's ciphertext doesn't decrypt under another's key), the full two-phase flow (request leaves keys untouched; confirm destroys them and flips status), ciphertext proven unrecoverable post-confirmation, double-confirm and unknown-request-id both raising, the erasure-fact commit landing in storage with no PII in its payload, and re-provisioning a fresh key generation (and old ciphertext staying unrecoverable) after a subject is erased and returns. Full suite rerun (`uv run python -m pytest tests/`): 115 passed, 1 skipped, no regressions. Out of scope for this pass (as with prompt versions in 1.6): automatic wiring into `instrumentation.py`'s per-span hot path — spans don't carry a `subject_id` field today and not every span field is subject-linked PII, so a host app calls `encrypt_for_subject`/`decrypt_for_subject` explicitly on the fields it knows are tied to a data subject. |
| 2.3 | Tamper-evident hash-chained audit log with externally anchored Merkle roots | 🏅 Certified | Each entry embeds hash of previous; root anchored outside operator's control; broken-chain detection test passes | PRD §7. Entry-level chaining lives directly on `StorageCommit` (feature 2.1) in [wisetraceloom/storage.py](../wisetraceloom/storage.py) — `entry_hash` (SHA-256 over `prev_hash` + every other field on the row, via the shared `compute_entry_hash`) and `prev_hash` (the prior version's `entry_hash`, `None` for a stream's first commit), computed inline in `append_commit`'s existing OCC retry loop so it's recomputed fresh on every retry rather than risking a stale chain link. Hit and fixed a real bug during development: SQLite round-trips a `datetime` column via SQLAlchemy as **naive** even when written timezone-aware, so a freshly-read-back `committed_at.isoformat()` silently differed from the string used when its hash was first computed, breaking every entry's chain on the very next read regardless of tampering — fixed with `iso_utc()`, used consistently on both the write and verify paths. Verification and Merkle anchoring live in the new [wisetraceloom/audit_chain.py](../wisetraceloom/audit_chain.py) (kept separate from storage.py the same way checkpoint.py already is): `verify_chain` walks a stream's commits recomputing each `entry_hash` and confirming `prev_hash` linkage, returning the first broken version rather than just true/false; `compute_merkle_root` (standard pairwise SHA-256, odd-leaf duplicated) plus `anchor_commits`/`verify_anchor`/`AnchorRecord` implement the "root anchored outside operator's control" half of the acceptance criteria — `anchor_commits` hands `(stream_id, root)` to a caller-supplied `AnchorSink` callable rather than shipping any default network sink, since a root anchored by code this same operator controls proves nothing per PRD §7's own framing; the host is responsible for wiring a sink to something genuinely external (separate-trust-domain object storage, a timestamping authority, an HSM/KMS-signed record, ...). `verify_anchor` only re-checks local consistency (recomputed root still matches what was anchored) — verifying `external_reference` against the real external anchor is deliberately outside this codebase's reach, documented as such rather than faked. Verified by 18 tests in [tests/test_audit_chain.py](../tests/test_audit_chain.py): chain linkage on first/second commits, empty-stream and untampered-stream verification, tampered-payload and re-linked-chain detection (both correctly reporting the exact broken version), per-stream isolation, chain integrity surviving 20 concurrent writers (`ThreadPoolExecutor`, mirroring feature 2.1's own concurrency test), Merkle root edge cases (single leaf, empty-list rejection, order-sensitivity, determinism), and the anchor round-trip (sink invocation args, persisted reference, `verify_anchor` true when untampered and false when `entry_hash` itself is forged post-anchor — the case an external anchor exists specifically to catch, since a self-consistent local rewrite could otherwise fool `verify_chain` alone). **Follow-up robustness fix (found while building feature 2.4)**: the concurrent-writers test above was intermittently failing `append_commit`'s OCC retry budget — `_prev_entry_hash`'s extra read per attempt (needed for the hash chain) widened the window in which many concurrent writers observe the same stale "next version" before any commits, so a 20-way thundering herd occasionally needed more than the original 5 retries to converge, even though no writer was ever actually lost. Fixed in `append_commit` (storage.py) by raising `max_retries`'s default to 20 and adding a small jittered backoff before each retry (standard OCC contention-reduction — desynchronizes retriers so each round resolves more of them), confirmed stable across repeated runs afterward.
